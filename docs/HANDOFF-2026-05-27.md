### 1b. Calendar consolidation — what to know (commit `bf2afbd`)

- **Before:** "Touch Base" tasks on the same day merged into one calendar event for that lead, but "Send Proposal" / "Send Summary" / custom labels each got their own separate event. Jordan's calendar was showing 3 separate events for the same person on the same day.

- Lives in `server/src/routes/tasks.ts` — see the create/update handlers that look up an existing event for the lead+date pair before creating a new one.

### 1c. CSV import — Apify + expanded aliases (commits `9e0448e`, `bc92b26`)

- Lives in `server/src/routes/leads.ts` — the CSV import route at the bottom of the file.

### 1d. Dedupe — what it does now (commits `661abc7`, `73b2654`)

Lives in `server/src/routes/leads.ts` around lines **395–650**. Endpoint: `POST /api/leads/dedupe { dryRun?: boolean }`. Wired into Settings → Lead Cleanup → "Find & merge duplicate leads".

**Three passes:**

| Pass | What it catches |
|---|---|
| **1. Phone match** | Same phone, normalised to last 9 digits (so `+61 412 345 678`, `0412 345 678`, `412345678` all collapse to the same key) |
| **2. Name + company** | For leads with no usable phone — exact match on lowercase `name + '|' + company` |
| **3. Business-name-as-name** *(commit 73b2654)* | When a lead's `name` equals its `company` (e.g. "Method Recruitment" / "Method Recruitment"), it folds into the real-person lead at the same company. At most ONE real person per company is ever pulled into a biz-dup group |

**Survivor scoring** (after grouping, who do we keep?):

```
score = notes_count
      + tasks_count
      + emails_sent_count
      + call_logs_count
      + activities_count
      + (manually_contacted ? 1 : 0)
      + (pipeline_stage = 'pulse' ? 1 : 0)
      + (deal_value > 0 ? 1 : 0)
      + (consolidated_summary IS NOT NULL ? 1 : 0)
```

Highest score wins. Ties broken by **oldest id** (most established record).
Losers' notes / tasks / emails / call_logs / activities are all reassigned
to the survivor BEFORE the loser is deleted — so nothing is lost.

The preview card now shows each group as e.g.:

> *Phillip Riley · +61 3 9192 9920 · 2 copies*
> *Survivor: lead #142 (activity score 7) · deleting #289*

`survivorScore` is wired through the API and into the client
`DedupeResult` type (`client/src/services/api.ts`).

>

> so that no matter when I dump leads in there, if any of the data
> matches, it highlights it and I can decide what to do with the
> duplicate lead: fold or delete.

### What he's saying, in plain English

1. The current 3-pass dedupe still has gaps — there are duplicates in
   his data that the system isn't surfacing.
2. He wants a **union-find / cross-field match**: if ANY of (name,
   company, phone) match between two leads, group them as candidates.
3. **Critical safety rule:** when merging, if the SURVIVOR has a direct
   mobile (Kate Shute's personal mobile) and the loser has a head-office
   landline (Method Recruitment's main switchboard), the head-office
   number must NOT overwrite Kate's direct mobile during the merge.
   Likewise, don't overwrite Kate's email with the company's
   info@methodrecruitment.com.au.
4. He wants the **preview to be a decision UI**, not just a confirmation
   — for each group, he wants to choose **fold** (merge keeping the
   survivor's contact details) or **delete** (drop the duplicate without
   merging activity).

### Where the code lives

- `server/src/routes/leads.ts` lines **395–650** — the `POST /api/leads/dedupe` handler. Three passes today (phone / name+company / biz-name-as-name).
- `client/src/pages/SettingsPage.tsx` — the "Lead Cleanup" UI, preview list, merge button.
- `client/src/services/api.ts` — `dedupe()` function, `DedupeResult` type with `survivorScore`.

### Recommended implementation strategy

This is the approach the previous session would've taken if it could
have responded. Sanity-check it against what Jordan actually wants
before you start coding.

**Step 1 — Union-find grouping.** Replace the 3 separate passes with a
single union-find pass:

- Build three keys per lead: `phone_key` (last 9 digits), `name_company_key` (lowercased), `biz_key` (when name == company).
- For each pair of leads that share ANY non-empty key, union them.
- Each connected component becomes a candidate dup group.

**Step 2 — Field-level merge plan (NOT whole-record overwrite).**
For each group, compute a survivor (same activity-score logic as today),
then for each field on the loser:

- `phone` — only copy to survivor if survivor's `phone` is empty.
  Direct mobile beats head-office. NEVER overwrite a non-empty survivor
  phone with a loser phone.
- `email` — same rule: only fill if survivor is empty.
- `website` — only fill if survivor is empty.
- `name`, `company` — same rule.
- `notes` / `tasks` / `emails_sent` / `call_logs` / `activities` —
  always reassigned to survivor (these are append-only timelines, no
  conflict possible).
- `deal_value` — keep survivor's, OR sum, OR keep the larger? **Ask
  Jordan before deciding.**

**Step 3 — Fold vs Delete per group in the UI.** The Settings preview
list needs two buttons per group:

- **Fold** → run the field-level merge above, reassign activity, delete losers.
- **Delete duplicates** → delete losers WITHOUT reassigning activity. Just nuke them.
- **(Optional) Skip** → leave this group alone for now.

The current "Merge N duplicates" button is all-or-nothing. Jordan wants
per-group control.

**Step 4 — Make the preview show the conflict.** For each group, render
the survivor's fields side-by-side with the loser(s)' fields, with a
visual marker on any field where they differ. E.g.

> *Kate Shute · Method Recruitment*
> *Survivor #142 — phone 0412 345 678 · email kate@method.com.au · score 8*
> *Folding #389 — phone 03 9192 9920 (different) · email info@method.com.au (different) · score 0*
> *On fold: survivor's phone + email kept. #389's empty fields would not overwrite. Both leads' notes/tasks/emails moved to #142.*

That gives Jordan the visibility he asked for: *"highlights it and I
can decide what to do with the duplicate lead: fold or delete"*.

### Don't break

- The existing safety rule that two genuine contacts at the same company are NEVER merged against each other (Pass 3 enforces this — keep that property).
- The append-only nature of activity rows. Never UPDATE an activity row — always re-FK.
- The "oldest id wins on tie" rule.
- The dryRun path. Both preview and actual merge run through the same handler with `dryRun: true|false`.

### What to verify after shipping

1. Jordan's "Method Recruitment + Kate Shute" case now shows up in preview.
2. Jordan's "Trade Wind Australia + Paul Smith" case now shows up in preview.
3. Folding a biz-dup never overwrites a real-person lead's mobile/email/website.
4. The per-group Fold vs Delete buttons work independently.
5. The preview shows the activity score for the survivor (existing behaviour — don't lose it).
